Mercan Yasama – Yürütme – Yargı

Bu proje, Mercan tool-use / agent sistemini üç ayrı mantıksal role ayırarak geliştirmek için oluşturulmuştur:

1. Yasama — Decision Maker / Router
2. Yürütme — Argument Filler / Tool Caller
3. Yargı — Response Composer

Amaç, tek bir modelin aynı anda tool seçme, tool argümanı üretme ve sonucu kullanıcıya anlatma görevlerini üstlenmesi yerine bu sorumlulukları açık biçimde ayırmaktır.

Bu repository aynı zamanda üç modülün:

* aynı veri sözleşmelerini kullanmasını,
* aynı action ontology üzerinden konuşmasını,
* aynı observation/state formatını paylaşmasını,
* bağımsız eğitilebilmesini,
* TRUBA üzerinde ortak dataset ve checkpoint düzeniyle çalışabilmesini,
* runtime sırasında birbirleriyle uyumlu kalmasını

sağlamak için ortak proje sözleşmesi görevi görür.

⸻

1. Temel Mimari

Mercan agent runtime akışı:

USER
  │
  ▼
YASAMA
  │
  │ selected action
  ▼
YÜRÜTME
  │
  │ JSON arguments
  ▼
VALIDATOR / POLICY
  │
  ▼
EXECUTOR
  │
  │ observation
  ▼
YASAMA
  │
  ├── yeni action ──→ YÜRÜTME
  │
  └── FINISH
        │
        ▼
      YARGI
        │
        ▼
       USER

Sistem statik bir plan üretmek zorunda değildir.

Her tool execution sonrasında oluşan yeni observation tekrar Yasama’ya verilir.

Dolayısıyla sistem:

plan once → execute everything

yaklaşımı yerine:

decide
→ execute
→ observe
→ decide again

şeklinde çalışan reaktif bir agent loop kullanır.

⸻

2. Üç Modülün Kesin Görevleri

Bu ayrım proje boyunca korunmalıdır.

⸻

2.1 Yasama

Yasama sistemin karar vericisidir.

Görevi:

user request
+ conversation history
+ current state
+ last observation
→ next action

Yasama yalnızca hangi action’ın yapılması gerektiğini seçer.

Argüman üretmez.

Doğru:

FILE_CREATE

Yanlış:

FILE_CREATE(path="notes.txt", content="Merhaba")

Argüman üretmek Yürütme’nin görevidir.

⸻

2.2 Yürütme

Yürütme, Yasama tarafından seçilmiş action’ı gerçek bir tool çağrısına dönüştürür.

Girdi:

user request
+ conversation history
+ state
+ selected action
+ tool schema
+ placeholder

Çıktı:

{
  "path": "notes.txt",
  "content": "Merhaba"
}

Yürütme’nin görevi:

ACTION
→ doğru JSON arguments

üretmektir.

Yürütme final kullanıcı cevabı üretmez.

⸻

2.3 Yargı

Yargı yalnız gerçek executor sonuçlarına bakarak kullanıcıya final cevap üretir.

Girdi:

original/current user request
+ relevant conversation history
+ real observations

Çıktı:

notes.txt dosyası oluşturuldu ve içine "Merhaba" yazıldı.

Yargı’nın temel kuralı:

Observation içinde bulunmayan hiçbir başarı, sonuç veya bilgi uydurulmamalıdır.

Executor hata döndürdüyse Yargı başarı iddiasında bulunamaz.

⸻

4. Source Action ve Canonical Action Ayrımı

Datasetlerde geçen her source tool adı zorla 16 canonical action’dan birine çevrilmemelidir.

Güvenli alias örnekleri:

web_search       → WEB_SEARCH
read_file        → FILE_READ
edit_file        → FILE_EDIT
list_directory   → FILE_LIST
search_code      → FILE_SEARCH
run_command      → SHELL_EXECUTE

Ancak semantic olarak birebir olmayan mapping yapılmamalıdır.

Örnek:

REQUEST_CONFIRMATION ≠ ASK_CLARIFICATION
send_message         ≠ SEND_MAIL
write_file           ≠ otomatik FILE_CREATE
calculator           ≠ CODE_EXECUTE

Bu yüzden datasetlerde şu alanların ayrı tutulması tercih edilir:

source_action
mapped_action
ontology_action
mapping_status
preserve_original

Örneğin:

{
  "source_action": "write_file",
  "mapped_action": null,
  "mapping_status": "unmapped_preserved",
  "preserve_original": true
}

Kaynak semantiği korunmalıdır.

⸻

5. Ortak Observation Contract

Executor çıktıları üç modül için ortak bir formata normalize edilmelidir.

Minimum canonical observation:

{
  "action": "FILE_CREATE",
  "data": {},
  "status": "success",
  "error": null
}

Alanlar:

action
→ hangi action/tool çalıştırıldı
data
→ executor'ın gerçek output payload'ı
status
→ success | error
error
→ hata yoksa null, hata varsa hata bilgisi

Ek provenance alanları bulunabilir:

tool_call_id
provider
source
execution_id

Ancak temel dört alanın semantiği değiştirilmemelidir.

⸻

6. Ortak State Contract

Minimum state:

{
  "completed_actions": [],
  "last_observation": null
}

Daha gelişmiş kullanımda:

{
  "completed_actions": [],
  "last_observation": null,
  "recent_observations": [],
  "step_index": 0,
  "turn_index": 0
}

kullanılabilir.

Önemli kural:

Aynı field üç farklı modülde farklı anlama gelmemelidir.

7. Yasama Training Formatı

Conceptual input:

user_prompt
+ conversation_history
+ state

Target:

target_action

Kod açısından:

target = row["target_action"]

Örneğin:

USER:
notes.txt dosyasını oluştur ve içine Merhaba yaz.
STATE:
{
  "completed_actions": [],
  "last_observation": null
}
TARGET:
FILE_CREATE

Tool execution sonrası ikinci Yasama örneği:

USER:
notes.txt dosyasını oluştur ve içine Merhaba yaz.
STATE:
{
  "completed_actions": ["FILE_CREATE"],
  "last_observation": {
    "action": "FILE_CREATE",
    "data": {
      "path": "notes.txt"
    },
    "status": "success",
    "error": null
  }
}
TARGET:
FINISH

Yasama’nın öğrenmesi gereken problem yalnız intent classification değildir.

Aynı zamanda:

state → next action

problemidir.

⸻

8. Yürütme Training Formatı

Conceptual input:

user_prompt
+ conversation_history
+ state
+ action
+ tool schema
+ placeholder

Target:

target_arguments

Kod:

target = json.dumps(
    row["target_arguments"],
    ensure_ascii=False
)

Örnek:

USER:
notes.txt dosyasını oluştur ve içine Merhaba yaz.
ACTION:
FILE_CREATE
PLACEHOLDER:
{
  "path": null,
  "content": null
}

Target:

{
  "path": "notes.txt",
  "content": "Merhaba"
}

Burada JSON gerçekten model output’udur.

⸻

9. Placeholder Politikası

Yürütme modeline yalnız tool schema vermek yerine gerektiğinde placeholder JSON verilebilir.

Örneğin:

{
  "path": null,
  "content": null
}

Modelin görevi:

yeni JSON structure icat etmek

değil,

verilen structure içindeki doğru alanları doldurmak

olur.

Bu özellikle küçük modellerde:

* ekstra key üretme,
* kapanmayan JSON,
* tekrar eden JSON,
* schema dışı alan,
* yanlış key spelling

problemlerini azaltabilir.

⸻

10. Yargı Training Formatı

Yargı için conceptual input:

user_prompt
+ relevant conversation_history
+ real observations

Target:

response

Kod:

target = row["response"]

Bu nokta özellikle önemlidir.

Dataset disk üzerinde şu şekilde tutulabilir:

{
  "user_prompt": "...",
  "observations": [],
  "response": "Final kullanıcı cevabı."
}

Ancak model target’ı:

Final kullanıcı cevabı.

olmalıdır.

Şu şekilde olmamalıdır:

{
  "response": "Final kullanıcı cevabı."
}

Çünkü assistant span başladıktan sonra üretilen bütün tokenlar gerçek final kullanıcı cevabıdır.

<|im_start|>system

kullanarak nihai cevabı üret. Gözlemlerde bulunmayan bilgi uydurma.
<|im_end|>

<tool_observations>

      "path": "notes.txt",
      "content": "Merhaba"
    },
    "status": "success",
    "error": null

Training sırasında:

observation        → MASK
assistant prefix   → MASK
assistant response → LOSS

Prompt tokenları target değildir.

12. Tool Role Kullanımı

Modelin tokenizer/chat-template’i yalnızca:

system
user
assistant

rollerini destekliyorsa yeni bir tool role zorla eklenmemelidir.

Observation şu şekilde user/context içerisine gömülebilir:

<tool_observations>
...
</tool_observations>

Chat-template değişiklikleri üç modülün birlikte kullandığı ortak contract’ın parçası olmalıdır.

⸻

13. Web Search Data Politikası

Büyük arac_kullanimi web-search verisinde bazı observation’lar çok fazla search result içermektedir.

Aktif compaction politikası:

web_search results
→ source ranking korunur
→ en alakalı ilk 3 sonuç tutulur

Örneğin:

[1]
[2]
[3]

kalır.

[4]...[10]

training context’ine alınmaz.

Amaç:

* context window’u gereksiz şişirmemek,
* en alakalı retrieval kanıtlarını korumak,
* Yargı’nın gereksiz snippet gürültüsü üzerinde eğitim almamasını sağlamak.

Bu işlem yalnız observation input’una uygulanır.

Final response target değiştirilmez.

⸻

14. Calculator Data Politikası

Calculator ailesinde kaynak function isimleri korunmalıdır.

Örnekler:

calc
calculator
calculate_discount
calculate_bmi
calculate_median
calculate_area
calculate_tip
calculate_tax
calculate_interest
...

Bunların tamamı otomatik olarak:

CODE_EXECUTE

action’ına map edilmemelidir.

Calculator source schema’sı Yürütme için değerlidir.

Observation result da değiştirilmeden korunmalıdır.

Örnek:

{
  "action": "calculate_median",
  "data": {
    "median": 5
  },
  "status": "success",
  "error": null
}

Calculator result’larında truncation yapılmamalıdır.

36. Runtime Protocol

Minimum:

1. user request alınır
2. state oluşturulur
3. Yasama action seçer
4. action canonical tool registry'de çözülür
5. Yürütme arguments üretir
6. JSON parse edilir
7. schema validation yapılır
8. policy validation yapılır
9. gerekiyorsa confirmation alınır
10. executor çalışır
11. observation normalize edilir
12. state update edilir
13. Yasama yeniden çağrılır
14. FINISH gelirse Yargı çağrılır
15. final cevap kullanıcıya döner

⸻

37. Runtime Safety

Minimum korumalar:

max step limit
repeated action+arguments detection
repeated error detection
path sandboxing
shell sandboxing
code sandboxing
destructive action confirmation
tool output prompt injection filtering
schema validation
observation grounding

Yasama veya Yürütme model output’u tek başına yetkili executor komutu kabul edilmemelidir.

⸻

38. Tool Registry

Production ortamında merkezi bir tool registry olmalıdır.

Örneğin:

{
  "FILE_CREATE": {
    "description": "...",
    "parameters": {
      "path": {
        "type": "string"
      },
      "content": {
        "type": "string"
      }
    },
    "required": [
      "path",
      "content"
    ],
    "side_effect": true,
    "confirmation_required": false
  }
}

Yasama action ontology ile Yürütme tool schema aynı registry üzerinden türetilirse interface drift riski azalır.

⸻

39. Yasama Evaluation

Minimum metrics:

action accuracy
macro-F1
next-action accuracy
FINISH accuracy
clarification accuracy

Özellikle zor pair’ler:

FILE_READ vs FILE_SEARCH
FILE_CREATE vs FILE_EDIT
WEB_SEARCH vs WEB_OPEN
RESPOND vs TOOL
FINISH vs CONTINUE

ayrı ölçülmelidir.

⸻

40. Yürütme Evaluation

Minimum:

JSON validity
exact key/schema match
per-field accuracy
whole-call exact match
wrong-value leakage
correction handling
negation handling
missing argument handling

Örneğin:

"Önce output.txt demiştim ama final.txt kullan."

target:

{
  "path": "final.txt"
}

olmalıdır.

⸻

41. Yargı Evaluation

Minimum:

observation faithfulness
success/error correctness
hallucination rate
critical-field recall
JSON-copy rate
natural response quality

Özellikle şu hata ciddi kabul edilmelidir:

observation.status = error
model:
"İşlem başarıyla tamamlandı."

⸻

42. Üç Model Arası Integration Evaluation

Tek modellerin metric’leri yeterli değildir.

End-to-end test gerekir.

Örnek:

USER:
main.py dosyasını oku, portu 8080 yap ve testleri çalıştır.

Beklenen:

Yasama → FILE_READ
Yürütme →
{"path":"main.py"}
Executor → content
Yasama → FILE_EDIT
Yürütme → correct edit args
Executor → success
Yasama → SHELL_EXECUTE
Yürütme →
{"command":"pytest"}
Executor →
12 passed
Yasama → FINISH
Yargı →
main.py içindeki port 8080 olarak güncellendi ve 12 testin tamamı geçti.

⸻

43. Physical Model Topolojisi

Mimari mantıksal olarak üç modüldür:

Yasama
Yürütme
Yargı

Ancak fiziksel olarak iki model olabilir.

Örnek:

ModernBERT
→ Yasama
Mercan 0.8B
├── Yürütme
└── Yargı

Yürütme ve Yargı aynı checkpoint’te multitask eğitilecekse görev açık biçimde ayrılmalıdır.

Örneğin:

<TASK_ARGUMENT_FILL>

ve:

<TASK_RESPONSE>

gibi task mode’ları kullanılabilir.

Bu konu kesin training tasarımı belirlenirken versionlanmalıdır.

44. Değişiklik Yönetimi

Interface değiştiren her önemli karar şu sırayla uygulanmalıdır:

1. ortak contract güncellenir
2. schema/ontology version gerekiyorsa artırılır
3. dataset builder güncellenir
4. verifier güncellenir
5. dataset yeniden üretilir
6. role-specific formatter test edilir
7. role-specific model eval yapılır
8. end-to-end integration test yapılır

Bir değişiklik yalnız tek modülde sessiz şekilde uygulanmamalıdır.

Örneğin:

observation schema değişti

ise kontrol edilmesi gerekenler:

dataset
Yasama state builder
Yargı formatter
runtime normalizer
integration tests

olmalıdır.

[ ] Yargı için grounded final response var mı?

48. Yasama Çalışmasına Başlarken Checklist

[ ] yalnız canonical/eligible action rows kullanılıyor mu?
[ ] target sadece action mı?
[ ] arguments target'a sızıyor mu?
[ ] source action ile canonical action karışıyor mu?
[ ] current state doğru oluşturuluyor mu?

[ ] FINISH örnekleri var mı?
[ ] class imbalance kontrol edildi mi?

49. Yürütme Çalışmasına Başlarken Checklist

[ ] selected action input'ta açık mı?
[ ] doğru tool schema kullanılıyor mu?
[ ] placeholder key'leri doğru mu?
[ ] target sadece arguments JSON mu?
[ ] source schema korunuyor mu?
[ ] correction/negation örnekleri var mı?
[ ] malformed JSON metric'i ölçülüyor mu?

⸻

50. Yargı Çalışmasına Başlarken Checklist

[ ] observation prompt tarafında mı?
[ ] success/error grounding korunuyor mu?
[ ] tool result'ta olmayan bilgi target'ta var mı?
[ ] historical assistant cevapları yanlışlıkla loss'a giriyor mu?
